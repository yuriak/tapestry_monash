# Federated Training Validation Progress Report

**Reporting date:** 7 August 2026  
**Coverage:** Phases 1–7

Phase 8 was subsequently accepted; its independent cross-cluster report is
available in [`20260811_phase8_report.md`](20260811_phase8_report.md).

## Executive Summary

This work established an end-to-end validation path for LoRA supervised
fine-tuning through progressively more realistic federated execution. The
sequence began with single-accelerator and distributed training, then isolated
adapter state transfer and aggregation correctness, introduced the Rust/Python
runtime boundary, connected two real peer processes, moved that exchange across
separate compute hosts, and finally completed a substantive five-round
federated training run on non-IID data. The primary objective was not to build a
production training platform or optimize the upstream implementation. It was to
determine whether the current training stack can execute the complete workflow,
preserve model-state correctness across boundaries, and produce a model that
learns on held-out data. That objective has been met.

The experiment code added during this effort is deliberately external to the
upstream source. It includes portable environment activation and dependency
locking, scheduler-aware launchers, deterministic dataset preparation,
checkpoint compatibility handling, adapter-delta encoding and application,
FedAvg aggregation, Rust/Python bridge implementations, peer lifecycle
controllers, direct-address transport setup, evaluation utilities, process
cleanup probes, and fail-closed phase verifiers. Generated model, dataset, and
runtime state remains separate from the reusable experiment source.

## Phase 1: Training, Distributed Execution, and Resume

Phase 1 established the basic supervised fine-tuning contract with a pinned
Qwen3-0.6B base model, a rank-8 LoRA adapter, and a deterministic conversational
dataset sample. The single-accelerator test completed BF16 forward and backward
passes, produced finite metrics, changed the adapter parameters, and wrote a
complete checkpoint. The distributed test then launched two explicit workers,
verified one accelerator per rank, maintained synchronized LoRA state, and
completed a 20-step training run.

The fresh-process continuation test initially exposed an upstream checkpoint
path defect: the resume wrapper discovered a step directory and passed that
directory to a loader that expected the checkpoint root, causing an apparent
resume to restart at step zero. A dedicated compatibility launcher was written
to restore the model, optimizer, cursor, and deterministic scheduler progress
without modifying upstream source. With that boundary in place, a new process
restored the exact step-20 LoRA state and emitted only steps 21–30. Phase 1
therefore validated single-device training, multi-device synchronization,
checkpoint completeness, and genuine stateful continuation rather than a
silent fresh run.

## Phase 2: Canonical Adapter Update Round Trip

Phase 2 isolated the state transition required for federated learning. A local
training run captured its initial adapter, completed four optimizer steps, and
exported the dense FP32 parameter difference as a canonical safetensors delta.
A separate process applied the delta to the initial adapter, while another
fresh process loaded the reconstructed state and completed a further optimizer
step. This separation ensured that success could not depend on Python object
identity or residual in-memory state.

The phase introduced reusable code for adapter schema validation, finite-value
checks, state hashing, atomic safetensors output, dense delta construction,
delta application, and fresh-load verification. The accepted update contained
112 tensors and 1,146,880 non-zero values. Applying it reproduced the trained
adapter with a maximum absolute error of approximately `2.91e-11`, well below
the `1e-7` acceptance threshold, and the continuation process loaded the
applied state with zero measured error. This established a precise and portable
model-update representation for the later network phases.

## Phase 3: One Real Peer and the Rust/Python Boundary

Phase 3 replaced the direct Python invocation with a real peer process from the
upstream Rust implementation. The Rust node launched an experiment-specific ML
bridge, the bridge trained on exactly one scheduler-visible accelerator, and
the returned delta was recorded as an API-visible `ModelUpdate`. The test
decoded the network payload and compared it byte-for-byte with the canonical
delta, then independently checked the SHA-256 digest, tensor schema, finite
values, non-zero count, and Rust history-chain hash.

Supporting work for this phase included a workspace-local Rust toolchain
bootstrap, isolated Cargo build output, a runtime-directory generator for the
hard-coded ML-engine entry point, dynamic port selection, an HTTP lifecycle
probe, and a verifier that rejects placeholder or malformed updates. The node
completed its training checkpoint, exposed exactly one valid model update, and
shut down without leaving Rust, Python, or training-runtime processes behind.
This demonstrated that the canonical update contract survived the actual
language and process boundary.

## Phase 4: Deterministic Two-Client FedAvg

Phase 4 tested the federated algorithm independently of network behavior. Two
logical clients received deterministic, disjoint shards and trained from an
identical global adapter. Each emitted a dense delta, after which a dedicated
aggregator computed equal-weight FedAvg and reconstructed the next global
state. Both clients then started fresh optimizer states from that aggregate and
repeated the process for a second round.

The new phase-specific code covered deterministic client sharding, common-base
capture, independent client launch, sample-weighted delta aggregation, global
adapter reconstruction, and a per-round mathematical oracle. All four client
trainings completed, the client deltas were non-zero and distinct, and both
rounds used weights summing to one. Aggregate-delta and global-state
reconstruction errors were exactly zero. The second round also loaded the first
round's global adapter with zero error, proving the intended transition from
local updates to a new shared initialization.

## Phase 5: Two Real Peers on a Shared Host

Phase 5 combined the previous training and aggregation contracts with two real
Rust peers. Each peer had isolated accelerator visibility, ports, persistent
state, training runtime, checkpoints, and data. Public discovery was disabled;
the second peer joined through the first peer's explicit endpoint identity and
direct address. Both APIs had to show bidirectional Gossip membership before
training began.

Across two rounds, both peers trained concurrently, broadcast canonical
base64/zlib/safetensors updates, staged the remote payloads, validated their
hashes, and independently computed the same equal-weight aggregate. Their
global adapters matched exactly, and their update histories and trust
leaderboards converged. Additional controllers and probes were written for
multi-peer startup ordering, endpoint capture, direct seed construction,
peer-specific runtime isolation, history inspection, controlled termination,
and persistent-state recovery.

The restart probe confirmed that endpoint identity and the known-peer cache
survived, while update history did not. It also exposed that peer reviews can
bind to a newer update than the one evaluated and that record signatures are
currently placeholders. These findings were documented as upstream
limitations rather than hidden by the experiment harness. The phase met its
training, aggregation, transport, and cleanup acceptance criteria.

## Phase 6: Direct Transport Across Compute Hosts

Phase 6 changed the placement boundary while keeping the Phase 5 learning
contract deliberately small. One peer ran on each of two independently
scheduler-isolated hosts. The controller resolved private host addresses,
started the first peer, captured its real endpoint identity, and passed an
explicit endpoint-and-address seed to the second peer. Multicast discovery,
distributed lookup, DNS discovery, and public relay were disabled, so a
successful mesh demonstrated a direct host-to-host QUIC/Gossip path.

The dedicated two-host controller used host-pinned task launch, propagated the
scheduler's logical accelerator assignment, captured execution evidence from
both peers, and performed allocation-scoped cleanup checks after termination.
All local trainings completed, the two histories and leaderboards converged,
and both peers independently reconstructed the same aggregate with zero
maximum error. Restart preserved identity and the known-peer entry, but showed
that the persisted entry lacks the dialable address needed for autonomous
reconnection. Phase 6 therefore proved direct cross-host transport and clean
lifecycle management while defining a precise, narrower recovery claim.

## Phase 7: Substantive Federated Training and Convergence

Phase 7 scaled the validated path from a lifecycle test to a substantive
federated fine-tuning experiment. It retained the same strict boundaries proven
in earlier phases—fresh optimizer state for every local round, canonical dense
adapter deltas, independent aggregation on both peers, real Gossip transport,
and fail-closed verification—but increased both the data volume and the amount
of learning by several orders of magnitude. The experiment was run in two
placements, once with both peers sharing a host and once with the peers on
separate hosts. The data, model, optimizer, aggregation, and acceptance
contracts were identical in both cases.

### Dataset and non-IID partition

The source was the `train` split of `databricks/databricks-dolly-15k`, pinned to
immutable revision `bdd27f4d94b9c1f951818a7da7fd7aeea5dbff1a` under its
CC BY-SA 3.0 license. Each source record was converted to a two-message ChatML
conversation. When the original row contained context, that context was
appended to the user instruction before tokenization. Empty instructions or
responses were rejected.

The partition was deterministic, disjoint by source index, and intentionally
non-IID by task category. For each peer, the first 1,152 eligible records were
used for training and the following 128 records were held out. The category
counts below cover the complete 1,280-record local partition before the
train/validation split.

| Peer | Assigned categories | Category counts | Training examples | Held-out examples |
|---|---|---|---:|---:|
| Peer A | Closed QA; open QA; information extraction | 335; 670; 275 | 1,152 | 128 |
| Peer B | Brainstorming; creative writing; summarization | 608; 247; 425 | 1,152 | 128 |

This arrangement ensured that neither peer saw the other peer's task families
locally. The combined workload contained 2,304 training examples and 256
held-out examples, while each peer still had enough local data to make ten data
epochs materially different from the earlier smoke tests. Source indices,
materialized-file hashes, resolved configuration hashes, and tokenization
metadata were retained for verification.

### Model and local-training configuration

The base model was the pinned `Qwen/Qwen3-0.6B` checkpoint. Only LoRA parameters
on the query and value projections were trainable; the resulting adapter had
112 tensors and 1,146,880 trainable parameters. Every federated round started
from the previous global adapter in a new training and checkpoint directory,
with a fresh optimizer and scheduler. This made each round an explicit
federated warm start rather than a continuation of stale client optimizer
state.

### Federated protocol configuration

Two peer processes participated in five learning rounds. During each round,
both peers loaded the same global adapter, trained independently on their local
non-IID shard, and exported the difference between their trained and starting
adapters. The canonical update was a finite dense FP32 safetensors state. It was
compressed with zlib, base64 encoded for the Rust record, and transmitted over
the Gossip mesh. On receipt, the experiment bridge decoded the exact bytes,
checked the SHA-256 digest against the sending peer's round output, and rejected
schema, shape, key, hash, or finite-value mismatches.

| Federated item | Value |
|---|---|
| Participating peers | 2 |
| Training rounds | 5 |
| Finalization calls | 1 additional aggregation-only invocation per peer |
| Aggregation | Equal-weight dense FedAvg |
| Client weights | Peer A 0.5; Peer B 0.5 |
| Round transition | `G(r) = G(r-1) + 0.5 × ΔA(r) + 0.5 × ΔB(r)` |
| Update representation | FP32 safetensors delta |
| Wire representation | `base64(zlib(safetensors))` |
| Exchange mechanism | Direct peer-to-peer QUIC/Gossip |
| Expected participants | 2 |
| Federation epoch | 600 seconds |
| Synchronization deadline | 570 seconds after the epoch boundary |
| Public discovery and relay | Disabled for the direct-transport run |
| Global-state tolerance | Maximum absolute error no greater than `1e-7` |
| Evaluation points | Fresh loads of G0, G1, G2, G3, G4, and G5 |
| Evaluation batch size | 4 |
| Expected final history | 12 ModelUpdates and 20 PeerReviews |

The sixth ML-bridge invocation is important to interpreting the record count.
Five calls train and publish the local Round 1–5 deltas; the sixth consumes the
Round 5 peer delta and produces G5 without starting another local training run.
Each peer therefore contributes six ModelUpdate records and ten PeerReview
records over the complete lifecycle. Both peers must end with the same 32
unique record hashes and with byte-equivalent logical tensor states for every
global adapter.

### Phase-specific implementation

The dedicated Phase 7 code extended the earlier test harness in the following
areas:

- deterministic Dolly materialization, category-disjoint partitioning,
  ChatML conversion, tokenization, and provenance manifests;
- a persistent five-round bridge state machine with a distinct final
  aggregation-only transition;
- round-bound delta hash binding, compatible-schema validation, atomic global
  adapter output, and independent FedAvg execution on both peers;
- peer lifecycle controllers for both shared-host and separate-host placement,
  including direct seed construction, execution evidence, timeout handling,
  controlled termination, and process-residue checks;
- fresh-process G0–G5 held-out evaluation and final text generation; and
- a fail-closed verifier for data disjointness, 50-epoch training evidence,
  per-round global equality, history convergence, held-out improvement, source
  integrity, and cleanup.

### Observed training time and utilization

The full separate-host workflow took approximately 58.5 minutes from process
startup through final evaluation and cleanup. About 50 minutes of that elapsed
time came from five fixed ten-minute federation epochs. Initial setup and
alignment to the next common epoch boundary consumed roughly seven minutes, and
fresh evaluation of G0–G5 took approximately one minute.

| Timing component | Observed duration | Interpretation |
|---|---:|---|
| GPU-active 720-step training interval | 145–157 seconds per peer per round | Actual accelerator-intensive optimization |
| Complete train/verify/delta ML invocation | Approximately 186–207 seconds | Includes runtime startup, model loading, checkpointing, verification, and update creation |
| Configured federation epoch | 600 seconds | Fixed wall-clock round interval |
| ML completion to next epoch | Approximately 406–414 seconds | Peer propagation barrier plus enforced wait to the next boundary |
| Five training rounds plus G5 finalization | Approximately 50 minutes | Measured from the first training boundary to the final aggregation boundary |
| G0–G5 held-out evaluation | Approximately 1 minute | Six fresh adapter evaluations, with generation at G5 |
| End-to-end experiment | Approximately 58.5 minutes | Includes setup, boundary alignment, training, aggregation, evaluation, and cleanup |

The measured GPU duty cycle was therefore only about 24–26%. This was not a
training or transport stall. The Rust loop detected that both participants
were available, but still slept until the configured 570-second deadline and
then aligned to the next 600-second boundary. The conservative interval was
useful for the first full run because it left ample room for model loading,
training, checkpointing, update exchange, and review propagation. For this
exact workload, the measurements indicate that a 300-second epoch would likely
retain adequate margin while approximately halving the inter-round idle time.
An event-driven barrier based on receipt of both current-round updates would be
the preferable long-term design.

All ten local training runs completed 720 optimizer steps with finite losses.

adapter.

Both peers independently reconstructed exactly the same global tensor state in

Round 1 to `0.01079` in Round 5, showing that updates remained non-zero while
their magnitude gradually contracted.

The final macro NLL was `2.331795`, a `26.96%` relative improvement over G0.
Peer A finished at NLL `2.244909` and perplexity `9.44`; Peer B finished at NLL
`2.418681` and perplexity `11.23`. A fresh process loaded G5 with zero measured
adapter-state error and generated a non-empty response. The network histories
also converged exactly: both peers exposed the same 32 unique hashes, with six
ModelUpdates and ten PeerReviews from each logical origin. No peer, Python
worker, training runtime, or accelerator process remained after controlled
shutdown.

Phase 7 therefore demonstrated the target claim in full: the current code can
train meaningful non-IID local workloads, exchange and validate real adapter
updates, repeatedly aggregate them across peers, preserve identical global
state, and deliver a model with substantially improved held-out likelihood.
The G2 validation minimum also provides a concrete direction for later work:
global validation and early stopping should determine the useful number of
federated rounds rather than assuming that additional local epochs will always
improve generalization.

## Overall Assessment

The seven-phase progression now provides evidence for every essential link in
the current baseline training path: deterministic data preparation, local LoRA
training, multi-accelerator execution, exact checkpoint continuation,
canonical delta production, fresh-process state reconstruction, mathematically
correct FedAvg, Rust/Python interoperability, real peer-to-peer update exchange,
direct cross-host transport, repeated global aggregation, held-out evaluation,
and clean shutdown. The final experiment did not merely complete mechanically;
it reduced macro held-out negative log likelihood from `3.192470` to `2.331795`,
a relative improvement of `26.96%`, while maintaining exact agreement between
the peers' global models.

The work also produced a clear boundary between validated experimental
capability and unresolved production concerns. Checkpoint-path handling,
history persistence, authenticated records, peer-review version binding,
address recovery, error propagation, and synchronization efficiency require
upstream attention before operational deployment. They do not prevent the
current code, with the documented experiment-side compatibility layer, from
completing foundational federated training and producing a measurably improved
model.
